# Development

## Architecture

Raindown runs inside the plugin, in [ruby.wasm](https://github.com/ruby/ruby.wasm), Ruby compiled to WebAssembly, in a Web Worker, so typing never waits for it. `src/engine.js` starts the worker, `src/worker.js`, which starts Ruby once, loads Raindown, and then answers each write-back on the Ruby it kept running, with `src/engine.rb`. Starting takes about a second, and each write-back after that a few milliseconds. The plugin applies what Raindown wrote back through Obsidian, and only if the note hasn't changed since, so nothing you type is lost. Notes without directives, like `<!-- toc: -->`, or `raindown: true` in their front matter, don't start Raindown.

Ruby can't wait for Obsidian to read a file, so the worker has a copy of the vault's notes, data files and `.raindown` folders in Ruby's in-memory folder, at `/vault`, sent as it starts and as they change. The files Raindown writes, like a table's CSV, come back with each answer, and the plugin writes them through Obsidian. Obsidian doesn't say when a hidden file changes, so each write-back checks the `.raindown` folders first, and starts Raindown again when they've changed, so their nodes load again. Raindown's given the front matter Obsidian's already read, and told which files changed at each write-back, rather than reading every note, or checking their modified times, for a `list:`, which takes seconds in a vault of thousands of notes in WebAssembly.

WebAssembly has no processes or sockets, so Ruby waits on the worker, through ruby.wasm's `evalAsync`, or JSPI, below, for what needs them, which `src/worker.rb` asks for: an endpoint's request, which the worker sends to Obsidian's main thread, for `requestUrl`, and a project's JavaScript components, which run in the worker, imported from their text, rather than in Node.js. Raindown's services, `raindown` in a node's context, are answered by the worker too, for Ruby nodes, through `Raindown::Services.host`, and for JavaScript ones, through Raindown's `services.js`, which `bin/build` puts before the worker's code: files from its copy of the vault, which go back with the answer like a table's CSV, `fetch` through `requestUrl`, a cache in IndexedDB, by vault, and no `git`. So the worker answers one request at a time. Commonmarker is native too, so reading view's `<{ }>` sections are rendered by Raindown as Markdown, with `commonmark: false`, then by Obsidian's `MarkdownRenderer`.

## Building

Obsidian loads one file, `main.js`, which `bin/build` builds from `src/`, with Raindown's files and ruby.wasm's two modules, each compressed with gzip, in Z85, a base 85 a fifteenth smaller than base64, which the worker decompresses with the browser's own `DecompressionStream`. That starts Raindown about 100 ms sooner than xz, which is a third smaller. CI compresses it with [zopfli](https://github.com/google/zopfli), which makes gzip a tenth smaller, in about half a minute, and a build without zopfli uses Zlib's. Edit `src/`, not `main.js`, which git ignores, as CI builds it for a release. It needs a checkout of Raindown, at `../raindown` or `RAINDOWN_DIR`, and its gems, and `wasm/Gemfile`'s, `rbwasm` and the `js` gem, installed in the plugin's Ruby, in `.ruby-version`. That's ruby.wasm's Ruby, 4.0.0, rather than Raindown's own, as only the standard library files that load natively are packed, from ruby.wasm's, and a later patch release loads different ones. With [wasmtime](https://wasmtime.dev), as `WASMTIME`, it also compiles Raindown to bytecode, which halves how long it takes to load. Then only the bytecode's packed, with each source file left empty, but for `rbconfig.rb`, which loads before the bytecode can, as Ruby needs to find a file to require it, which makes `main.js` smaller. It downloads ruby.wasm into `build/` the first time.

```sh
BUNDLE_GEMFILE=../raindown/Gemfile bundle install
BUNDLE_GEMFILE=wasm/Gemfile bundle install
WASMTIME=~/.wasmtime/bin/wasmtime bin/build
```

Raindown's packed into a ruby.wasm module of the plugin's own, which `scripts/ruby_wasm.rb` builds the first time, as ruby.wasm's npm package builds its own, but with only the extensions Raindown and a vault's nodes use. It leaves out OpenSSL, as Obsidian makes the plugin's HTTPS requests, and WebAssembly has no sockets, and tools' extensions, like ripper, and the transcoders for Chinese, Japanese and Korean character sets, through Ruby's own `--no-transes`, as Raindown reads UTF-8, which every language's text in Obsidian is in. Converting a Shift_JIS or Big5 file, like `text.encode('UTF-8', 'Big5')` in a vault's Ruby node, raises in Obsidian. Building it compiles Ruby for WebAssembly, which takes a while, so it's kept in `build/module`, and CI caches it. It's built again when the script, `wasm/Gemfile.lock` or a patch changes. A vault's node that requires an extension that's left out fails to load it.

Ruby's source is patched as it's built, with `wasm/patches`, for how it jumps in WebAssembly, which has no `setjmp`. Ruby's own there is Asyncify's, which unwinds every call frame to the root and rewinds them each time it's called, so Ruby avoids it while running Ruby code, but not in its C, like `Hash#each`, `Mutex#synchronize`, `catch`, `require`, `==` on an array, or reading a file, which take 10 to 35 times as long as native Ruby, where Ruby code takes 2 to 3 times. The patch catches those jumps as Ruby code's are caught, so a write-back never calls `setjmp`, and keeps the buffers Ruby allocates for each call of a block from C. `test/vault/jumps.md` rescues, breaks and throws thousands of times in one request, in the smoke test, and `scripts/jumps.js`, which `bin/build` runs after it, checks each of the 95 cases in `test/ruby/jumps.rb`, of exceptions, `break`, `throw`, `ensure`, `retry`, Fibers, enumerators, `require` and files, some under `GC.stress`, gives what native Ruby gives, run directly and in a Fiber. Run it again on its own with `node scripts/jumps.js build/raindown.wasm build/runtime/npm-4.0/package/dist/browser.umd.js build/root`, or the module without Asyncify, `build/raindown-jspi.wasm`.

`wasm/patches/ruby-4.0-wasm-shapes.patch` gives Ruby's shape tree its 280 MB from fresh WebAssembly memory, which is already zeroed and only backed by the OS as it's touched, as `mmap`'s is natively, rather than from wasi's emulated `mmap`, which allocates and zeroes all of it as Ruby starts, taking 150 to 200 ms.

The module's already built for speed, with `-O3`, by Clang and by Binaryen's `wasm-opt`, and a newer Binaryen, or `-O4`, measured no faster. Asyncify still instruments most of Ruby, as an exception, a Fiber or garbage collection, which reads the stack through it, can unwind from nearly anywhere, so it can't be limited to a list of functions safely.

So `main.js` has a second module, without Asyncify, which the worker uses where the engine has JSPI, JavaScript Promise Integration, as Obsidian's desktop app's Chromium does, and Asyncify's where it hasn't, like Safari, on iPhones and iPads. It runs Ruby 1.5 to 2 times as fast, but for `catch` and `throw`, and starts it in three quarters of the time. `scripts/ruby_wasm.rb --jspi` builds it with `wasm/patches/jspi` and the shapes patch, rather than the jumps patch, from a wasi-sdk with LLVM 19 or later and Binaryen 131, which `bin/build` downloads into `build/runtime`, or are `WASI_SDK_PATH` and `BINARYEN`. setjmp is WebAssembly's exception handling, garbage collection only runs between requests, as it can't read WebAssembly's locals, which keeping on the stack in memory would cost 15 to 25%, so a request's garbage stays until it's answered, and the engine starts Ruby again once its memory, which never shrinks, is past 512 MB and it's had no request for 30 seconds, or past 1 GB and nothing's waiting for it, and each Fiber's a JSPI stack, which only switches in Ruby the worker called through `WebAssembly.promising`, so it answers through `rb_wasm_jspi_eval`, and Ruby waits for it with `RbWasmJSPI.wait`, rather than `evalAsync`, as the patch says. wasi-vfs can't compile exception handling, so neither module's packed with Raindown's files, but `main.js` has them once, with the js gem's, and the worker gives them to Ruby in its in-memory folders. [wasm/experiments/without-asyncify](wasm/experiments/without-asyncify) has how it was worked out and timed.

`scripts/trace.rb` writes back `test/vault`, with a note for each of Raindown's directives, and lists the Ruby files that loaded, so only those are packed. A directive that loads a file the vault doesn't would fail in the plugin, so give the vault a note using it.

Starting Raindown is timed step by step: decoding and decompressing the module, compiling it, unpacking Ruby's files, starting Ruby, loading Raindown and copying the vault in, which the engine reads meanwhile, once the worker says it's begun, so a big vault's read takes nothing from starting. The engine sends the worker only the module it'll run, and Ruby reads its bytecode from Ruby's files as one, with an index, rather than opening each file. Obsidian's console shows it as `Raindown started`, with which module, in milliseconds from when the worker began each step, and the smoke test prints how long each took, with the first write-back's. After each answer, the worker sends back only the files Ruby opened to write or renamed, rather than checking every file in the vault.

Once `main.js` is built, `scripts/smoke.js` runs its worker, with Raindown in WebAssembly, in Node, on a copy of `test/vault`, and fails the build unless each note's written back as native Raindown wrote it in `scripts/trace.rb`. So a file missing from the module, or a ruby.wasm update that breaks the worker, is caught before a release. It runs with Asyncify's module, with JSPI hidden, as in Safari, then with the one without it, with Node 26's JSPI, as do the jumps below. Without Node, `bin/build` skips it, except in CI, which always runs it. Run it again on its own with `node scripts/smoke.js`, or `RAINDOWN_WITHOUT_JSPI=1 node scripts/smoke.js` for Asyncify's.

`bin/build` builds Components too, the plugin for beginners, into `build/components`, with its own `main.js`, the manifest in `components/manifest.json`, at the plugin's version, and `styles.css`. It's this plugin with `src/edition.js` naming the Components edition: only Markdown Components, in a vault's `Components` folder, which Obsidian shows, none of Raindown's own nodes, endpoints or table editing, a "New component" command, and Raindown in its Components edition too, as the worker tells it. It stays off while Raindown's plugin is on, which does all it does, rather than both writing back each note. Its release goes to a repository of its own, [rainpour/obsidian-components](https://github.com/rainpour/obsidian-components), as Obsidian lists each plugin from one: only CI writes there, with `COMPONENTS_TOKEN`, a secret of this repository's, a token that can write to that one's contents, with `scripts/mirror_components`. Each push to `main` copies its own files, like its README, from `components/repository`, which is where they're changed, and each release the plugin's source too, as Obsidian needs a plugin's source in its repository, with its manifest and versions, which Obsidian reads its version from, then releases it at the same version, with its files. Without the token, neither happens, with a warning. Changing its workflows, in `components/repository/.github`, needs the token to be able to write workflows too.

## Testing

The tests run outside Obsidian, with a stub of Obsidian's API, and a stand-in for Raindown. Editing as it's typed, like lining up tables, and what Enter and Tab do in a table's cells, is Raindown's `lib/raindown/js/editing.js`, which the app edits with too, so the tests take it from Raindown's checkout, at `../raindown` or `RAINDOWN_DIR`, as `bin/build` does:

```sh
npm test
```

To link it into a vault while you work on it, `ln -s "$PWD" VAULT/.obsidian/plugins/raindown`, then build it, and reload Obsidian. Building again is needed after changing Raindown too.

### Releasing

Obsidian installs a plugin from its GitHub repo's releases, so the plugin is released from a repo of its own, with this folder as its root. `bin/bump` runs `npm version minor`, or `patch` with `--patch` or `-p`, or `major` with `--major`, which sets the version in `package.json` and `manifest.json`, adds it to `versions.json` with the oldest Obsidian it runs on, and tags it without a `v`, like `0.2.0`, as Obsidian needs, then pushes it. CI then runs the tests, builds `main.js` with Raindown at `RAINDOWN_VERSION`, a tag like `v0.19.0`, or a commit, runs the smoke test, and attaches `main.js`, `manifest.json` and `styles.css` to a release, with an attestation that CI built them. It builds and smoke tests each push to `main` too. To build with a new Raindown, release it, then set `RAINDOWN_VERSION` to its tag:

```sh
bin/bump # minor
bin/bump --patch
bin/bump -p
bin/bump --major
```
